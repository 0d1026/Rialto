**Design proposal, not implemented.** No DHT client exists in this repo. This page
explains the mechanism in enough depth to build from later; it is not a description of
running code. What's actually built today - `POST /federation/register`,
`GET /federation/peers`, and a manual catalog-ingestion CLI - is described accurately
in [Architecture](/docs/architecture) §3.2 and covered from a risk-accounting angle in
the [threat model](/docs/threat-model) §6. The decision record behind this proposal is
[ADR 0003](/docs/decisions/federation-dht-discovery).

## The problem, precisely

Today, a facilitator is only findable by Rialto if it already knows Rialto exists and
calls `POST /federation/register`, or if a Rialto operator already knows about it and
manually runs the ingest CLI against it. Both directions require the two parties to
already be aware of each other by some out-of-band means. That's fine between two
operators who've talked to each other; it doesn't answer "how does a brand-new,
independent facilitator become findable by the wider x402 ecosystem without
individually introducing itself to every index that might carry it."

That's a lookup problem with a specific shape: _given a key, find who holds the value
for it, without asking a central party_. That shape has a well-known solution.

## Kademlia from first principles

Kademlia is a distributed hash table: a way for a network of nodes to collectively
store and look up key→value pairs with no coordinator, where every node knows a
little about the network and any node can find any key in a small, bounded number of
hops. It's the same peer-discovery primitive BitTorrent's Mainline DHT (BEP 5) and
IPFS's content routing are built on.

### Node IDs and the XOR distance metric

Every node picks (or derives) an ID in the same address space as the keys it will
store - conventionally a 160-bit or 256-bit number. **Distance** between two IDs `a`
and `b` is:

```
d(a, b) = a XOR b        (interpreted as an unsigned integer)
```

That's a real distance metric - `d(a,a)=0`, `d(a,b)=d(b,a)`, and it satisfies the
triangle inequality - which is what lets independently-run routing tables agree on
"who is near this key" without comparing notes. The property that actually matters for
routing: for any node and any distance, there is exactly one other node at exactly
that distance. Every node's neighborhood is well-defined no matter who's looking.

### k-buckets: a small routing table that still finds anyone

A node keeps, for each distance range `[2^i, 2^(i+1))` from its own ID, up to `k`
contacts (Kademlia's paper uses `k=20`; BitTorrent's Mainline DHT uses 8) - a
**k-bucket** per range. The result: fine-grained knowledge of the ID-space
neighborhood right around a node's own ID, and only a handful of signposts for each
of the wide, far regions of the rest of the network. Total table size is
`O(k log n)` - a few hundred contacts, bounded, even for a network with millions of
participants.

### Looking something up: iterative, and fast

To resolve a key, a node asks its closest known contacts for _their_ closest known
contacts to that key, repeats against whoever's now closest, and stops when a round
returns nothing closer than what's already been found. Each round roughly halves the
remaining distance to the target, so this converges in `O(log n)` hops - a
million-node network resolves in roughly 20 hops. This is the exact mechanism that
makes BitTorrent DHT lookups and IPFS content routing fast at real internet scale.

**Worked example**, small enough to check by hand (4-bit space, real deployments use
160+ bits): target key `K = 1001`, and a node looking it up knows four contacts:

| contact | ID     | `K XOR contact` | decimal distance |
| ------- | ------ | --------------- | ---------------- |
| A       | `1000` | `0001`          | 1                |
| C       | `1011` | `0010`          | 2                |
| D       | `0001` | `1000`          | 8                |
| B       | `0110` | `1111`          | 15               |

A is closest (distance 1 - it differs from `K` in only the lowest bit). The lookup
queries the closest known contacts first; if none holds the value directly, they
return _their_ closest-known contacts to `1001`, which - because they're already near
the target - typically close the remaining gap in the very next round.

## The same primitive BitTorrent and IPFS use

Both systems draw the same line this proposal draws: **the DHT stores pointers, never
the payload.**

- **BitTorrent Mainline DHT** - key = a torrent's infohash, value = the swarm's peer
  list. A client resolves the infohash, then downloads the file over a **direct**
  peer-to-peer connection - never through the DHT.
- **IPFS content routing** - key = a content identifier, value = a provider record
  ("peer X has this block"). A client resolves the CID, then fetches the block over a
  **direct** connection to that provider.

Rialto's proposal is the same shape one level up: key = a facilitator's node ID,
value = `{baseUrl, catalogUrl}` - a pointer, not the catalog. The catalog is always
fetched with a direct HTTPS request to the facilitator the pointer names.

## Presence discovery: the planned DHT record

This is the DHT's presence layer: it answers "is this facilitator ID reachable, and
where." The next section extends the same record shape to answer a related but
distinct question - "who holds the best answer for this resource" - without a second
protocol or a second kind of client.

```
key   = facilitator node ID   (derivation: open question, see ADR 0003)
value = {
  baseUrl:    string   # e.g. https://facilitator.example.com
  catalogUrl: string   # the discovery feed this facilitator exposes for pulling
}
```

A new facilitator joins by contacting a small set of well-known bootstrap nodes,
performing a lookup for its own ID (which simultaneously populates its routing table
and announces its presence), then storing its own record. Looking up a _specific_
peer whose ID is already known is a direct lookup. Discovering peers you don't
already have an ID for is a different problem than what Kademlia alone solves -
BitTorrent and IPFS both lean on a secondary rendezvous convention for that; Rialto's
design would need the same, named here as an open gap rather than assumed solved.

### Resource-pointer records: the same mechanism, one level down

The record above is keyed by a _facilitator's_ node ID - it answers "how do I reach
this specific facilitator." The same DHT, with no new RPCs and no second protocol,
can also hold records keyed by a _resource identifier_ - the same identifier the
discovery catalog already indexes services under:

```
key   = resource identifier   (an existing catalog entry's identifier)
value = {
  facilitatorNodeId: string   # who to ask for this resource
  baseUrl:           string   # that facilitator's HTTPS origin
}
```

A lookup for a resource identifier resolves exactly the way a facilitator lookup
does - iterative FIND_VALUE, terminating in `O(log n)` hops. The only difference from
the presence record is what the key names; the routing, storage, and lookup mechanics
underneath are identical. The next section describes where these records come from:
nobody publishes one speculatively - each is a byproduct of a live query that already
confirmed a facilitator holds a strong answer for that resource.

## Query-time fan-out with DHT-backed resource selection

A DHT resolves a known key to a value in bounded hops. It cannot enumerate unknown
content - there's no way to ask it "everything relevant to X" the way a search index
can. That's not a shortfall to work around, it's a difference in what problem is
being solved, and this design uses the right tool for each: the DHT for presence and
pointer resolution (above), and query-time fan-out for coverage beyond the local
catalog.

This is not an improvised workaround. Federated and distributed information
retrieval has solved "which of several independent collections should this query be
sent to" for decades, under the name **resource selection** (sometimes collection
selection): a broker receives a query, decides which backend collections are worth
querying for it, sends the query to those, and merges the results. Meta-search
engines and distributed enterprise search systems both work this way. What follows
is that approach, applied to a federation of Bazaar catalogs, with one refinement
that fits naturally on top of the DHT above.

### The base mechanism

1. A search is answered locally first, BM25 plus embeddings against the requesting
   facilitator's own catalog ([lexical](/docs/search/lexical-bm25),
   [dense retrieval](/docs/search/dense-retrieval)), exactly as designed elsewhere in
   this project. No network round-trip is required for this step.
2. For broader coverage, the same query is also sent live to the set of peer
   facilitators already known through presence discovery. Each peer runs the query
   against its own catalog and returns results.
3. Results are merged and re-ranked at the querying node, using the same
   settlement-history and relevance signals used for local results.
4. The response honestly reflects its own completeness: if fan-out wasn't performed,
   or if a queried peer didn't respond in time, `partialResults: true` is set - the
   same field already used elsewhere in this project for any degraded-but-honest
   result set.

This alone gives real, useful coverage beyond a single node's own catalog, bounded by
which peers that node has discovered, and paid for only when a query actually asks
for it, not as constant background traffic.

### DHT-backed resource selection: the network improves itself over time

Every fan-out query produces information worth keeping: which peer, for a given
resource or query pattern, actually returned the strongest result. Rather than
letting that information disappear after one query, it feeds back into the DHT using
the resource-pointer record above:

- After a fan-out query resolves, the querying node publishes (or refreshes) a DHT
  record for the resource identifier that scored best, pointing at the facilitator
  that hosts it - exactly the `{facilitatorNodeId, baseUrl}` pointer shape defined
  above.
- The next node that needs that same resource identifier can resolve it directly by
  DHT lookup, no fan-out required, because a previous query already did the work of
  finding the right peer and left a pointer behind.
- Fan-out and DHT lookup are not competing strategies - they compose: fan-out is how
  the network discovers good answers the first time, the DHT is how that discovery is
  preserved and reused by everyone after. The network's DHT-resolvable coverage grows
  organically from real query traffic, with no separate crawl, sync, or
  full-replication step ever required.

This is the property worth naming clearly: coverage is not fixed at design time and
it is not paid for by constant background replication. It grows as the network is
used, converging toward broad DHT-resolvable coverage for anything actually being
searched for, while resources nobody has queried yet simply haven't been indexed into
the DHT - which is the correct, efficient behavior, not a gap.

### What this deliberately does not claim

For completeness and consistency with this page's existing standard of honesty about
tradeoffs: a resource hosted by a facilitator that has never been reached by presence
discovery, fan-out, or a prior query remains genuinely undiscoverable until one of
those three finds it. This is the same starting condition every federation design
has, gossip included - a network can only know what it has, directly or
transitively, connected to. What this section adds is that once _any_ node's query
surfaces a good result, that discovery is preserved and shared for everyone after,
rather than being repeated or lost.

## Why not a full libp2p node

|                       | libp2p                       | This proposal's scope                                                                |
| --------------------- | ---------------------------- | ------------------------------------------------------------------------------------ |
| Transport negotiation | TCP, QUIC, WebSocket, WebRTC | One: HTTPS - every facilitator already runs an HTTPS server                          |
| Stream multiplexing   | Yes                          | Not needed - discrete request/response, no long-lived streams                        |
| NAT traversal / relay | Yes                          | Not needed - facilitators are operator-run public services, not devices behind a NAT |
| Pubsub                | Yes                          | Not needed - discover-then-pull is a poll model, not a broadcast one                 |
| Kademlia DHT          | One module among many        | The entire thing needed                                                              |

Pulling in a full libp2p stack to get to its one relevant module means adopting its
whole transport/security/muxer negotiation surface for a narrower problem than the
framework is built to solve. A client scoped to exactly the four Kademlia RPCs (ping,
store, find-node, find-value) is small and auditable - and there's nothing in the
protocol that requires UDP as a transport. An HTTP-transported variant would keep the
whole federation stack to "things that speak HTTPS," consistent with the rest of
this project - the current leaning, not yet a final decision.

## The data plane: direct pull, no relay

Once a peer's `baseUrl`/`catalogUrl` is resolved - by DHT lookup in this proposal, or
by manual registration today - fetching its catalog doesn't change: a plain HTTPS
GET, direct, no intermediary. This is exactly what today's manual ingestion CLI
already does for external catalogs; the proposal only changes _how the URL is found_,
never _how it's fetched_.

**What "no relay hop" means, precisely**: no third server sits between the requesting
facilitator and the source, forwarding or rewriting the catalog payload. If a design
instead routed every pull through a relay, that relay becomes a place a listing could
be silently altered in transit - and the only way to catch that is for the source to
sign every entry end-to-end so the requester can verify the relay didn't tamper with
it. A direct connection removes the hop tampering would happen at, so it removes the
need for the signature scheme that would otherwise have to catch it. TLS between the
two parties already guarantees the requester receives exactly what the source sent.

**What doesn't change**: every pulled entry still runs through the same integrity
gauntlet that validates a live settlement's metadata - unconditionally, regardless of
provenance. The DHT and the direct pull only change _how a peer is found_ and _how
its catalog is fetched_, never how much that catalog's content is trusted once it
arrives. A malicious facilitator with a perfectly valid DHT record and a perfectly
direct HTTPS connection can still only get entries in that pass the same gauntlet
everything else does.

## Impact

Stellar services stay discoverable across the wider x402 ecosystem without needing a
gossip network's operational weight, a full libp2p node's dependency surface, or a
single registry's single point of control - closing the open interop question
[stellar/x402-stellar#50](https://github.com/stellar/x402-stellar/issues/50) without installing a new central party in its place.

## Threat model, briefly

Full accounting lives in the [threat model](/docs/threat-model) §6. In short: a DHT
adds Sybil/eclipse-style attack surface against the _lookup_ step (a known, studied
weakness of vanilla Kademlia, with known mitigation families). It does **not** add any
new way to get untrusted content trusted - that boundary is the integrity gauntlet,
and it doesn't move regardless of how a peer was discovered. Resource-pointer records
carry the same category of risk, not a new one - a forged one wastes a follow-up
HTTP round-trip at worst, since the response still has to pass the gauntlet like
anything else pulled in.

## What's not decided yet

- Node ID derivation - random, or tied to a facilitator's own signing key/domain.
- Bootstrap node list - who runs the first ones, how new deployments find them.
- Record lifetime - TTL, republish interval, offline handling.
- Record authenticity - whether the classic Sybil-forged-record weakness needs a
  dedicated fix, or is adequately covered by the integrity gauntlet catching bad
  content regardless. Applies to resource-pointer records too, including the fact
  that any node can publish one about itself after a fan-out query.
- Fan-out scope and cost - how many peers a query fans out to, and any timeout/backoff
  policy, isn't decided; today's `/federation/peers` list would be the starting point
  for "which peers," unchanged by whether DHT-based discovery ships.
- Transport - HTTP-carried Kademlia (current leaning) vs. classic UDP.
- Build vs. adopt an existing Kademlia implementation.

See [ADR 0003](/docs/decisions/federation-dht-discovery) for the full decision record.
