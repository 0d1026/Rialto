Rialto is an **x402 payment facilitator and Bazaar discovery layer for Stellar** - so AI
agents can find, pay for, and verify paid services on `stellar:testnet` and
`stellar:pubnet`.

## The problem, measured

x402 lets software pay for HTTP resources with an on-chain payment instead of an API key.
On Stellar, settlement already works - we verified it ourselves with real settled
transactions through the reference tooling and the official end-to-end test suite. What
is missing is **discovery**: an agent can only pay endpoints it was already told about.

We pulled the main public x402 catalog (Coinbase's Bazaar - 14,107 resources) in full and measured
Stellar's actual position in it:

- 518 entries advertise Stellar - but **92% belong to a single seller** listing Stellar
  alongside every other chain
- the remaining entries use malformed asset identifiers **no conformant Stellar client
  can settle**
- **zero** entries are Stellar-only, **zero** offer metered (`upto`) payments on
  Stellar, and **zero** MCP tools are cataloged in it
- the catalog's own search ignores network intent: querying for a Stellar service
  returns EVM results

Stellar is technically listed and practically invisible. Rialto exists to fix that.

## What Rialto builds

Built and tested end to end - not a plan, a running system:

1. **A facilitator** - canonical `/verify`, `/settle`, `/supported` on
   `stellar:testnet`, composing the Apache-2.0 `@x402/stellar` package rather than
   reimplementing settlement. `exact` scheme only so far; `upto` (below) is spec-only.
2. **A discovery catalog** - services are indexed automatically the moment a payment
   settles; no registration step. Validated against poisoning (the [integrity
   gauntlet](/docs/threat-model)), searchable with real hybrid ranking - keyword
   ([BM25F](/docs/search/lexical-bm25)) fused with semantic search
   ([embeddings](/docs/search/dense-retrieval)) - and ranked by real settlement
   history. Backed by a public, [re-runnable eval harness](/docs/search/evaluation-methodology)
   with [real numbers](/docs/benchmarks), not an unverified claim.
3. **Federation** - independent facilitators can self-register into an instance's peer
   list, and external catalogs (CDP, AlgoVoi) are pulled in directly over HTTPS via a
   manual CLI, through the same integrity gauntlet every entry gets. Cross-publishing
   isn't built yet, and discovery is manual - see below for the planned upgrade.

Still design-stage or spec-only, stated plainly:

4. **The `upto` payment scheme for Stellar** - the full [spec](/docs/scheme-upto-stellar)
   is written; the Soroban contract and facilitator integration aren't built yet.
5. **An MCP server** - so agents will eventually run discover → pay → verify from
   inside their own runtime. Today, the discovery HTTP API is callable directly (see
   the [buyer/agent guide](/docs/guides/buyers)) while the MCP wrapper is built.
6. **Federation peer discovery over a Kademlia DHT** - a proposal ([ADR
   0003](/docs/decisions/federation-dht-discovery), full mechanism on the
   [Federation](/docs/federation) page) to replace manual peer registration with the
   same peer-discovery primitive BitTorrent and IPFS use, so a facilitator becomes
   findable ecosystem-wide without registering with any single index. Catalogs would
   still be pulled directly over HTTPS from the source, no relay hop. The same DHT
   would also back query-time fan-out to peers, with resource-level pointers
   published back in so the network's searchable coverage grows from real query
   traffic instead of a crawl. Design only - no DHT code exists yet.
